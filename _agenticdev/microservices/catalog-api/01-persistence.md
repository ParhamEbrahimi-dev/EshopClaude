# Catalog.Api — 01 — Persistence

**Status:** Done

## Goal

Give Catalog.Api its own database schema in `catalogdb`, so later specs have somewhere to put and read products. The Product entity, the DbContext, the AppHost reference and the schema creation stay in one spec because none can be checked alone: the only proof is the products table in pgAdmin, and that needs all four.

## Context

- Catalog.Api today has only the placeholder `GET /` and the health endpoints from `MapDefaultEndpoints()`.
- Its csproj already references `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` (added in step 2a), so no package change is needed.
- The AppHost already declares `catalogdb` on the shared `postgres` server, but the `catalogapi` resource has no reference to it yet.
- **Connection string:** it comes only from the AppHost. `WithReference(catalogdb)` injects the environment variable `ConnectionStrings__catalogdb`, and `AddNpgsqlDbContext<CatalogDbContext>("catalogdb")` reads it. There is no fallback in `appsettings*.json`, so running Catalog.Api without the AppHost fails at startup. That is intended.
- **Schema creation:** `Database.EnsureCreated()` at startup, with no EF migrations. Aspire creates the empty `catalogdb` database. `EnsureCreated()` creates the table when the database has none and does nothing on later starts.
- **Naming:** EF Core defaults. Table `Products`, PascalCase columns. No naming-convention package.
- The Postgres container has no data volume, so every `aspire run` starts from an empty server. That's why the restart check below restarts only `catalogapi`.

## Depends on

Nothing.

## Data model

Entity `Product` maps to table `Products` in `catalogdb`, schema `public`.

| Property | C# type | Column | Postgres type | Constraints |
|---|---|---|---|---|
| Id | int | Id | integer | PK, identity (generated by default) |
| Name | string | Name | text | NOT NULL |
| Description | string | Description | text | NOT NULL |
| Price | decimal | Price | numeric(18,2) | NOT NULL |
| ImageUrl | string | ImageUrl | text | NOT NULL |

No max lengths, no indexes beyond the primary key, and no other columns.

## Tasks

5. Build, run, and go through every Definition of Done check.

## Definition of Done

1. `dotnet build` in `src/` prints `Build succeeded` with 0 errors.
2. `aspire run` in `src/`: the dashboard shows every resource Running/Healthy: postgres, pgadmin, catalogdb, orderingdb, redis, catalogapi, basketapi, orderingapi, webfrontend.
3. Dashboard → `catalogapi` → details → Environment variables include `ConnectionStrings__catalogdb`.
4. Dashboard → `catalogapi` → details lists `catalogdb` under its references / wait-for. During startup, `catalogapi` shows Waiting until `catalogdb` is Healthy.
5. HTTP `GET` on the `catalogapi` endpoint `/health` returns `200` with body `Healthy`. `GET /` returns `Catalog API is running.`
6. pgAdmin → Servers → postgres → Databases → catalogdb → Schemas → public → Tables lists `Products`.
7. pgAdmin Query Tool on `catalogdb`:
   ```sql
   SELECT column_name, data_type, is_nullable, numeric_precision, numeric_scale, is_identity
   FROM information_schema.columns
   WHERE table_name = 'Products'
   ORDER BY ordinal_position;
   ```
   Expect exactly 5 rows, matching the Data model:
   `Id` integer, NO, identity YES · `Name` text, NO · `Description` text, NO · `Price` numeric, NO, 18, 2 · `ImageUrl` text, NO.
8. pgAdmin Query Tool: `SELECT count(*) FROM "Products";` returns `0`.
9. Dashboard → `catalogapi` → Restart (only this resource): it comes back Healthy, its console log has no exceptions, and check 7 still returns the same 5 rows.
